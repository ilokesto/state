# persist

`persist` keeps state commits synchronous and manages asynchronous restoration, saving, and errors. Configure `key`, a `storage` factory, and a required `decode` function. Register it with `pipe.use(...)`, then create the store with `.create(initialState)`.

Creating a helper, middleware, or store performs no storage I/O and does not access `window`, `document`, or `indexedDB`. Start restoration explicitly with `await store.persist.rehydrate()`.

## Save and restore JSON state

Run this complete example in a browser module. It restores the previous theme, changes it to dark, and waits for saving to finish.

```ts lineNumbers
import { dispose, jsonStorage, persist } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

type ThemeState = { theme: 'light' | 'dark' };

const decodeTheme = (value: unknown): ThemeState | null => {
  if (typeof value !== 'object' || value === null || !('theme' in value)) return null;
  return value.theme === 'light' || value.theme === 'dark' ? { theme: value.theme } : null;
};

const store = pipe
  .use(persist({
    key: 'theme',
    storage: jsonStorage(() => window.localStorage),
    decode: decodeTheme,
  }))
  .create<ThemeState>({ theme: 'light' });

try {
  await store.persist.rehydrate();
  store.setState({ theme: 'dark' });
  await store.persist.flush();
} finally {
  dispose(store);
}
```

Handle rejected operations in the caller. Calling `setState` commits synchronously; it does not mean the value has reached storage.

## Choose an adapter

All helpers below are exported by `@ilokesto/state/middleware` and return a storage factory. Pass their result directly; do not add an outer `() =>`.

| Storage | `storage` option | Supported values |
| --- | --- | --- |
| IndexedDB | `indexedDBStorage({ database: 'my-app-state' })` | Structured-cloneable values |
| localStorage | `jsonStorage(() => window.localStorage)` | JSON values |
| sessionStorage | `jsonStorage(() => window.sessionStorage)` | JSON values |
| Cookie | `cookieStorage({ path: '/' })` | JSON values within cookie limits |

`jsonStorage` takes a getter to defer browser access. `jsonStorage(window.localStorage)` is not supported and evaluates a browser global during SSR. Web Storage itself remains synchronous; the persistence completion and error contract is asynchronous.

Factories can be reused across stores. Each activation creates an independent adapter instance, reused for that store's lifetime, not for each write. A custom factory needs no metadata. Its instance provides `getItem`, `setItem`, `removeItem`, and optionally `dispose` for owned resources. Factory creation failures can be retried; ordinary I/O failures do not recreate an existing instance.

## Native files and complex values

IndexedDB stores the `{ state, version }` envelope with structured clone. It preserves native `File` names, types and contents, plus `Blob`, `Map`, `Set`, `Date`, and `ArrayBuffer`, without base64 conversion.

```ts lineNumbers
import { indexedDBStorage, persist } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

type EditorState = { attachment: File | null; updatedAt: Date };

const decodeEditor = (value: unknown): EditorState | null => {
  if (typeof value !== 'object' || value === null) return null;
  if (!('attachment' in value) || (value.attachment !== null && !(value.attachment instanceof File))) return null;
  if (!('updatedAt' in value) || !(value.updatedAt instanceof Date)) return null;
  return { attachment: value.attachment, updatedAt: value.updatedAt };
};

const editor = pipe
  .use(persist({
    key: 'editor',
    storage: indexedDBStorage({ database: 'my-app-state' }),
    decode: decodeEditor,
  }))
  .create<EditorState>({ attachment: null, updatedAt: new Date(0) });

await editor.persist.rehydrate();
editor.setState({
  attachment: new File(['draft'], 'draft.txt', { type: 'text/plain' }),
  updatedAt: new Date(),
});
await editor.persist.flush();
```

Create image preview `blob:` URLs from restored blobs in the UI and revoke them when no longer needed. Do not persist those URLs. IndexedDB success means **transaction complete**, not merely request success. Uncloneable values, quota errors, and failed transactions reject saving. There is no automatic fallback to localStorage. JSON adapters do not preserve these native values: `Date.toJSON()` becomes a string, while `Map`, `Set`, `Blob`, and other unsupported values reject.

## Persist a typed projection

Full-state configurations remain unchanged. To save a subset, provide all three functions: `project(state: State): Persisted`, `decode(value: unknown): Persisted | null`, and `restore(persisted: Persisted, current: State): State`. The exported configuration type is `ProjectedPersistConfig<State, Persisted, Steps>`; `Steps` defaults to an empty migration tuple.

```ts lineNumbers
import { jsonStorage, persist } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

type Preferences = { theme: 'light' | 'dark'; search: string };
type SavedPreferences = Pick<Preferences, 'theme'>;

const decode = (value: unknown): SavedPreferences | null => {
  if (typeof value !== 'object' || value === null || !('theme' in value)) return null;
  return value.theme === 'light' || value.theme === 'dark' ? { theme: value.theme } : null;
};

const preferences = pipe.use(persist({
  key: 'preferences',
  storage: jsonStorage(() => window.localStorage),
  project: (state: Preferences) => ({ theme: state.theme }),
  decode,
  restore: (saved, current) => ({ ...current, theme: saved.theme }),
  saveDebounceMs: 200,
})).create<Preferences>({ theme: 'light', search: '' });

await preferences.persist.rehydrate();
preferences.setState({ theme: 'dark', search: 'not persisted' });
await preferences.persist.flush();
```

The stored envelope remains `{ state: projectedValue, version }`. `restore` explicitly decides what to retain; there is no automatic shallow or deep merge. It receives current memory state during hydration, and its result passes registered full-state validation before committing. Decoder rejection never invokes `restore`. Migration steps transform the persisted projection, and migration rewrites save only that projection.

Keep `project`, `decode`, and `restore` pure. Projection runs when the serialized writer processes a captured committed state, not inside the synchronous state commit. Coalesced commits need not invoke it. Projection failures leave the target pending with `INVALID_DATA`; restoration failures report `VALIDATION`. A changed projection does not migrate existing records implicitly: retain a compatible decoder or explicitly add data migrations.

## Explicit string codecs

`PersistCodec` is exported from `@ilokesto/state/middleware` with these final signatures:

```ts
type PersistCodec = {
  readonly serialize: (value: PersistedValue) => string;
  readonly deserialize: (text: string) => unknown;
};
```

Pass it as `jsonStorage(getStorage, codec)` or `cookieStorage({ codec, ...attributes })`. The codec owns serialization of the entire envelope; its unknown result still goes through envelope/version validation, migrations, and `decode`. Codec exceptions surface as `STORAGE` errors with their original cause.

This codec stores a `Date` state as milliseconds and restores its native type:

```ts lineNumbers
import type { PersistCodec } from '@ilokesto/state/middleware';

const dateCodec: PersistCodec = {
  serialize: (envelope) => {
    if (!(envelope.state instanceof Date)) throw new TypeError('Expected Date');
    return JSON.stringify({ state: envelope.state.getTime(), version: envelope.version });
  },
  deserialize: (text) => JSON.parse(text, (key, value: unknown) =>
    key === 'state' && typeof value === 'number' ? new Date(value) : value),
};
```

The application's decoder must still reject invalid dates. For nested data, the codec must explicitly handle the shapes it supports. Without a codec, JSON behavior and stored bytes are unchanged, including `Date.toJSON()` becoming a string. Changing a codec is an application-owned storage-format decision, not an automatic migration. IndexedDB already uses structured clone and does not accept or need this string codec.

## External storage synchronization

Synchronization is opt-in. Existing adapters and stores do not subscribe or reread automatically. For same-origin tabs sharing localStorage, provide an event source and enable `sync`:

```ts lineNumbers
import { jsonStorage, persist } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

const counter = pipe.use(persist({
  key: 'shared-counter',
  storage: jsonStorage(() => window.localStorage, undefined, { events: () => window }),
  decode: (value: unknown): number | null => typeof value === 'number' ? value : null,
  sync: {},
})).create(0);

counter.persist.subscribe(status => {
  if (status.error?.operation === 'sync') console.error(status.error.code, status.error.cause);
});
await counter.persist.rehydrate();
counter.setState(1);
await counter.persist.flush();
```

`jsonStorage(getStorage, codec?, options?: JsonStorageOptions)` keeps its existing arguments and bytes. `options.events` is a lazy getter for a window-like `addEventListener`/`removeEventListener` source. The adapter filters by storage area and key, including `Storage.clear()` events. Native storage events exclude the writing document, so this supports separate browsing contexts such as tabs, not multiple stores in one document. Separate browser profiles/private contexts do not share localStorage. sessionStorage only shares events within its own browser storage scope.

A custom `PersistStorage` may implement `subscribe(key: string, listener: () => void): () => void`. It must emit **external-only invalidations**, including deletes, and return an unsubscribe function. Without `sync`, this capability is never required. Opting into automatic sync without it rejects hydration with `STORAGE`. Native AsyncStorage/MMKV helpers do not invent a cross-process event transport.

`persist.sync(options?: PersistRehydrateOptions): Promise<void>` manually rereads current storage after successful hydration, including for adapters without events. It is distinct from `rehydrate()`, which remains a no-op after success. Automatic events use the optional policy in `sync: { conflict?: 'keep-current' | 'use-stored' }`; manual calls use their own argument.

| Local edits when the sync read starts or completes | Result |
| --- | --- |
| None | Restore the validated stored value without saving it back |
| No conflict policy | Reject with `CONFLICT`, retain local state and its pending save |
| `keep-current` | Retain local state and save it through the normal queue |
| `use-stored` | Explicitly replace local state and discard pending saves; their unfinished flushes reject with `CONFLICT` |

Automatic errors are observable through status with `error.operation === 'sync'`; hydration remains `hydrated`. Pending local edits retain normal saving behavior after a rejected sync. Pause saving while presenting a choice if the application must not overwrite either side before that decision. Resolve by calling `await counter.persist.sync({ conflict: 'keep-current' })` or `await counter.persist.sync({ conflict: 'use-stored' })`; there is no implicit merge.

Every invalidation rereads the latest durable value instead of applying an old event payload. A sync read waits for this store's active write/delete and holds later saves until its decision. Existing in-flight native writes cannot be rolled back: the read observes storage **after** they finish. This is not a distributed transaction or a total ordering across tabs. Concurrent edits can require application-level reconciliation.

External values follow the same envelope/version checks, migrations, decoder, projection `restore`, full-state validation, and history-baseline reset as hydration. External restoration never echoes a write or rewrites migrated data. A later user edit saves the current version normally. A delete or expired read retains memory and does not recreate storage by itself; conflict policies still govern unsaved local edits. A newer sync supersedes an older read (the superseded call resolves without applying). `clearStorage()` cancels pending reads with `CLEARED` and ignores events during its delete barrier; disposal cancels with `DISPOSED` and unsubscribes. Late reads cannot restore old data.

## Injected native storage

`asyncStorage(getStorage, codec?)` and `mmkvStorage(getStorage, codec?)` return lazy storage factories. They use the same default JSON envelope and optional whole-envelope `PersistCodec` as `jsonStorage`, without importing React Native or installing a native dependency:

```ts lineNumbers
import { asyncStorage, mmkvStorage } from '@ilokesto/state/middleware';
import type { AsyncStorageLike, MMKVStorageLike } from '@ilokesto/state/middleware';

export function nativeStorageFactories(asyncBackend: AsyncStorageLike, mmkvBackend: MMKVStorageLike) {
  return {
    asynchronous: asyncStorage(() => asyncBackend),
    synchronous: mmkvStorage(() => mmkvBackend),
  };
}
```

`AsyncStorageLike` requires `getItem(key): Promise<string | null>`, `setItem(key, text): Promise<void>`, and `removeItem(key): Promise<void>`. `MMKVStorageLike` requires `getString(key): string | undefined`, `set(key, text): void`, and `remove(key): boolean | void`. Inject operations matching these signatures; an application using a backend with `delete` instead of `remove` can supply an explicit structural adapter. The library does not guess native versions.

The native object is borrowed, not disposed or globally cleared. Only the configured key is read/written/removed. Native exceptions and rejected promises propagate to persistence errors, and `flush()` waits for the native write promise. A codec still produces untrusted data requiring decoding. These helpers provide neither encryption nor automatic account scoping.

## Explicit TTL and account switching

`ttlStorage(storage: PersistStorageFactory, options: TTLStorageOptions)` wraps any adapter with an explicit tagged format. `TTLStorageOptions` contains a positive finite `ttlMs` and optional `now: () => number` clock (default `Date.now`). It does not change any existing adapter or key automatically:

```ts lineNumbers
import { jsonStorage, ttlStorage } from '@ilokesto/state/middleware';

const shortLivedStorage = ttlStorage(
  jsonStorage(() => window.localStorage),
  { ttlMs: 30 * 60 * 1000 },
);
```

The opt-in stored shape is `{ state: { __persistTTL: 1, expiresAt, value: projectedState }, version }`. TTL unwraps it before migrations/decoding. Existing unwrapped entries and malformed metadata reject rather than being silently migrated or assigned an expiry. Choose an explicit application migration or clear the old entry before enabling this wrapper on an existing key. Codecs beneath TTL must support this wrapper shape, not only the inner state.

Expiry is checked after a read resolves, with `now() >= expiresAt` returning `null`. Expired reads do not delete storage because a concurrent writer may already have replaced it. There is no background timer, automatic memory reset, or renewal on reads. A write's deadline starts when the wrapper receives it, not when delayed native I/O completes. Use `clearStorage()` for physical cleanup. Optional external invalidations are forwarded; TTL does not generate clock events.

Account keys and store ownership remain application decisions. Stop old producers/UI editing first, pause saving, await `clearStorage()` when logout should erase that account, then dispose the old store and create a new one. Do not dispose before the awaited clear: native in-flight writes may otherwise finish after cleanup. If clear fails, handle the failure before reusing the same key. To keep account data instead, await `flush()` before disposal and omit clear.

```ts lineNumbers
import { dispose, jsonStorage, persist } from '@ilokesto/state/middleware';
import type { PersistStore } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

export async function switchAccount(previous: PersistStore<number>, nextAccountKey: string) {
  previous.persist.pause();
  await previous.persist.clearStorage();
  dispose(previous);
  const next = pipe.use(persist({
    key: nextAccountKey,
    storage: jsonStorage(() => window.localStorage),
    decode: (value: unknown): number | null => typeof value === 'number' ? value : null,
  })).create(0);
  await next.persist.rehydrate();
  return next;
}
```

Call this only after stopping updates to `previous`. The library never renames keys, migrates account storage, or reuses the previous account's in-memory state. A storage delete in another tab is not an authentication logout signal; coordinate authentication and store disposal separately.

## Lifecycle controls

| Control | Contract |
| --- | --- |
| `await rehydrate()` | Explicitly restore; concurrent calls share an attempt, success is a later no-op, failure is retryable |
| `await rehydrate({ conflict: 'keep-current' })` | Keep and save the current state after a restoration conflict |
| `await rehydrate({ conflict: 'use-stored' })` | Explicitly replace current state with validated stored state |
| `await sync(options?)` | Reread after hydration; apply the explicit pending-edit conflict policy |
| `await flush()` | Wait for the save target at call time; retry failed pending writes |
| `pause(): void` | Pause automatic saving; state commits and hydration continue |
| `resume(): void` | Resume saving the latest pending value, using the configured save debounce |
| `retry(): Promise<void>` | Retry the call-time target with the same guarantees as `flush()` |
| `await clearStorage()` | Delete only this key after older writes; keep the in-memory state |
| `getStatus()` | Read the latest immutable lifecycle snapshot |
| `subscribe(listener)` | Observe future snapshots; returns an unsubscribe function |

Edits before restoration completes stop restoration as a conflict by default. Neither memory nor storage is overwritten until the caller chooses a policy. There is **no automatic deep merge**. `flush()` before successful hydration rejects rather than overwriting unexamined stored data.

Saving is serial: one write runs while the waiting slot retains only the latest committed value. A failed write remains pending and is retried on a new commit or explicit `flush()`, without infinite automatic retries. `flush()` does not wait forever for future edits or force a state debounce timer to run. A successful `clearStorage()` prevents earlier pending writes from resurrecting the deleted value; a later user commit can save again. Waiting flush operations superseded by clearing reject with `CLEARED`.

`saveDebounceMs?: number` is available in both full-state and projected configurations. Omitted or `0` preserves immediate saving. A positive finite duration up to `2147483647` milliseconds restarts a save-only timer on each commit; it never delays state or subscriber notifications. It does not change the separate `debounce()` middleware or its ordering rules.

`pause()` cancels that timer but retains the latest pending state. An already started write and an outstanding flush obligation continue. `flush()` and `retry()` bypass both pause and the save timer without changing `paused`; they require successful hydration and may save a newer coalesced value to satisfy the captured target. Future commits do not extend a completed target. `resume()` restarts the save interval, or saves immediately without a configured delay.

`clearStorage()` is never paused: it discards older pending values and timers, rejects their flush promises, and queues deletion after active writes. Later writes remain behind the deletion barrier. Disposal cancels timers and rejects unfinished flush/retry operations with `DISPOSED`; synchronous `pause()` and `resume()` throw that error after disposal. Flush before disposal when saving is required.

## Observe status and errors

`getStatus()` and `subscribe()` replace `hasHydrated()` and `onRehydrateStorage`. Hydration is `idle`, `hydrating`, `hydrated`, `conflict`, or `error`; saving is `idle`, `writing`, or `error`. `pending` reports unsaved work, `paused` reports whether automatic saving is paused, `disposed` reports terminal persistence disposal, and `error` is a `PersistError` or `null`.

This fragment extends the `editor` example:

```ts lineNumbers
const unsubscribe = editor.persist.subscribe((status) => {
  if (status.error) {
    console.error(status.error.operation, status.error.code, status.error.cause);
  }
});
const status = editor.persist.getStatus();
const ready = status.hydration === 'hydrated';
unsubscribe();
```

Errors expose `operation`, a stable `code`, and the original `cause`. Rejected reads, migration, decoding, and validation preserve the current state. A notification failure after a commit does not roll back that commit or justify applying restoration again.

## Framework status bindings

All five framework subpaths export `bindPersistStatus(persist)`. Pass
`editor.persist`, not the state store. Its parameter is
`Pick<PersistControls, 'getStatus' | 'subscribe'>`; its result is that adapter's
`UseReadonlyState<PersistStatus>`. No writer or lifecycle controls are exposed.
The existing selector and optional equality arguments are preserved, including
Angular's `{ destroyRef }` options. Omitting equality uses the adapter's shallow
comparison; pass a custom equality function for nested selections.

For a saving indicator, extend the `editor` example with this React component:

```ts lineNumbers
import { createElement } from 'react';
import { bindPersistStatus } from '@ilokesto/state/react';

const useEditorStatus = bindPersistStatus(editor.persist);

export function SaveStatus() {
  const status = useEditorStatus();
  const label = status.error ? 'Save failed'
    : status.hydration !== 'hydrated' ? 'Loading'
    : status.saving === 'writing' ? 'Saving'
    : status.pending ? 'Unsaved changes' : 'Saved';
  return createElement('output', { 'aria-live': 'polite' }, label);
}
```

The other adapters expose the same status through their existing readonly shapes:

```ts
// Vue setup() or effectScope():
const useStatus = bindPersistStatus(editor.persist); // @ilokesto/state/vue
const { state: saving } = useStatus(status => status.saving); // saving.value

// Angular injection context, or pass an owned DestroyRef:
const useStatus = bindPersistStatus(editor.persist); // @ilokesto/state/angular
const { state: saving } = useStatus(status => status.saving, { destroyRef }); // saving()

// Solid component or createRoot():
const useStatus = bindPersistStatus(editor.persist); // @ilokesto/state/solid
const { state: saving } = useStatus(status => status.saving); // saving()

// Svelte: use $saving in a component, or unsubscribe a manual subscription.
const status = bindPersistStatus(editor.persist); // @ilokesto/state/svelte
const saving = status.select(snapshot => snapshot.saving);
```

These are independent snippets; import `bindPersistStatus` from the indicated
subpath. Full status includes `hydration`, `saving`, `pending`, `paused`,
`disposed`, and `error`. `binding.readOnly()` always reads current status outside
framework scope. React's server snapshot is the status captured when the binding
was created; create matching bindings before client restoration for SSR.

Creating a binding or calling `readOnly()` does not subscribe. Each active
framework subscription owns its own status connection and registry-store selector
filter. Unmount, scope disposal, `DestroyRef`, or Svelte unsubscribe releases that
connection. Multiple views can bind the same controls independently. There is no
factory-level connection to dispose, and disposing a view never disposes the
borrowed persistence or state store. The store owner still starts hydration,
handles rejected operations, flushes, and disposes the store.

## SSR and ownership

Use identical initial state on server and client. Start `rehydrate()` in a client effect, handle its rejected promise, and gate editing until `getStatus().hydration === 'hydrated'` if the feature does not offer conflict resolution. Subscribe before starting restoration so the UI sees every transition. No `skipHydration` option is needed.

The owner of a store calls `dispose(store)` when that instance is no longer needed. It cancels pending work and cleans up only its own connection, transactions, and subscriptions. A factory shared by two stores does not share this ownership. Late completions cannot mutate a disposed lifecycle. Disposal does not guarantee saving or undo a completed transaction: call `await store.persist.flush()` **before** disposal when saving is required.

## Middleware and migration

Persistence observes actual commits, not attempted writes. Validation rejection and throttle drops are not saved; deferred and reentrant commits are. Restoration follows read, envelope validation, migration, decode, explicit projection restoration when configured, registered state validation, and immediate commit. It bypasses debounce/throttle, runs state validation once, and becomes a new history baseline. User edits made by restoration listeners remain ordinary saved commits.

Declare `debounce()` before `persist()`; the reverse order remains rejected with `MIDDLEWARE_ORDER`. History supports either timer: undo/redo cancel pending timer work and replay synchronously through validation, and the resulting commit is persisted. Timer `flush()` forwards pending state updates; `store.persist.flush()` only waits for committed saves. Flush timers in pipeline order before awaiting persistence when pending updates must be saved.

All adapters support the same migration pipeline. Data version is the migration array length, distinct from IndexedDB schema version and internal commit sequence. See [Persist migrations](/en/state/advanced/persist-migrations) for the breaking API migration table and runnable examples.
