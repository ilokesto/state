# history

`history` records committed state transitions and adds undo/redo controls to the prepared store. Full snapshots remain the default; selection and typed patch strategies are opt-in.

## Signature

```ts lineNumbers
history(options?: { readonly limit?: number }): PipeAnyMiddleware
history<State, Selection = Readonly<State>, Patch = Selection>(
  options: HistoryOptions<State, Selection, Patch>,
): PipeMiddleware<State>
```

Both overloads add `HistoryControls` to the resulting store. The state-specific overload infers `State` from annotated hooks, or accepts explicit type arguments.

| Option | Contract |
| --- | --- |
| `limit` | Maximum undo entries, default `300`; a finite non-negative integer. A group counts as one entry. `0` disables entry retention. |
| `filter(previous, next)` | Record a committed transition only when this returns `true`. Receives full, readonly state snapshots after middleware validation. |
| `select(state)` | Select the value to record. Must be paired with `restore`. |
| `restore(current, selection)` | Reconstruct the full state, preserving untracked fields from `current`. Must be paired with `select`. |
| `isEqual(previous, next)` | Selection equality, default `Object.is`. Equal selections do not create entries or invalidate redo. |
| `strategy` | Typed `diff`/`apply` hooks; omit to retain selected snapshots. |

Use `HistoryStore<State>` when an API accepts a store with the controls, and `HistoryControls` when it accepts only the controls. Snapshots are retained by reference, not cloned: keep state, selections, and patches immutable.

## Example

{/* state-example:history-controls */}
```ts
import { history } from '@ilokesto/state/middleware';
import type { HistoryStore } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

const store: HistoryStore<{ count: number }> = pipe
  .use(history({ limit: 20 }))
  .create({ count: 0 });

store.setState({ count: 1 });
store.undo();
store.redo();
store.clearHistory();
```

`undo()` and `redo()` apply the recorded state through the store, so compatible middleware can observe and validate replay. A rejected replay retains its entry for retry. A committed replay moves its entry even if a body subscriber subsequently throws. `canUndo()` and `canRedo()` report whether a replay is available; `clearHistory()` removes entries without changing current state.

Replay carries `history/undo` or `history/redo` action metadata so logging and
DevTools can distinguish it from direct updates.

## Synchronous groups

```ts
const result = store.group(() => {
  store.setState({ count: 1 });
  store.group(() => store.setState({ count: 2 }));
  return 'updated';
});
// result: 'updated'; one undo returns count to 0
```

Nested callbacks share the outer group. Grouping does not batch state notifications or roll back changes: a thrown callback closes the group and rethrows, retaining its successful commits as one entry. Empty groups, rejected writes, and identical writes create no entries. A group that returns to its starting selection is still an entry; undo/redo can consume it without a body notification.

The first changed selection invalidates the redo branch. `undo()` and `redo()` inside an open group throw `TypeError`; call them after the callback. Promise-returning callbacks are rejected by the types and at runtime. Only the synchronous callback is scoped: never pass an async function or expect grouping to span `await`.

## Partial restoration and filters

```ts
type Editor = { text: string; cursor: number; remote: boolean };

const editor = pipe.use(history({
  select: (state: Readonly<Editor>) => state.text,
  restore: (current, text) => ({ ...current, text }),
  filter: (_previous, next) => !next.remote,
})).create({ text: '', cursor: 0, remote: false });

editor.set({ text: 'hello', cursor: 5, remote: false });
editor.set({ text: 'hello', cursor: 9, remote: false });
editor.undo(); // { text: '', cursor: 9, remote: false }
```

Filters skip entries, not commits. The next accepted transition starts from the actual current state, including earlier skipped changes. Filtering does not protect fields from older snapshots: use `select`/`restore` to keep cursor, network status, or other untracked fields out of undo. A fresh object returned by `select` needs an appropriate `isEqual` if equivalent selections should be ignored.

## Pause and resume

`pauseHistory()` stops recording new entries; `resumeHistory()` restarts it. Both are idempotent and leave existing undo entries intact. Undo/redo remain available while paused. A changed selected value invalidates redo even when paused or filtered, preventing replay of a stale branch; an untracked-only change does not.

Paused changes to selected fields are still subject to old snapshots or application-defined patches. To preserve a field across undo, exclude it from the selection rather than merely pausing its writes.

## Reactive metadata

```ts
import type { HistoryStatus } from '@ilokesto/state/middleware';

const snapshot: HistoryStatus = store.getHistoryStatus();
let undoEnabled = snapshot.canUndo;
const unsubscribe = store.subscribeHistory((status) => {
  undoEnabled = status.canUndo;
});
store.clearHistory(); // notifies metadata listeners even if the body is unchanged
unsubscribe();
```

`HistoryStatus` exposes readonly `canUndo`, `canRedo`, `undoDepth`, `redoDepth`, `isPaused`, `isGrouping`, and `disposed`. `getHistoryStatus()` returns a frozen snapshot with stable identity until the next metadata event. `subscribeHistory` does not emit immediately; read the current snapshot separately.

Recording, replay, clear, pause/resume, group boundaries, restoration, and disposal notify metadata subscribers. Body subscriptions alone cannot observe all these events. Delivery follows the registry Store's FIFO snapshot semantics, including independent duplicate registrations, unsubscribe cancellation, and aggregated subscriber errors. Subscriber errors do not roll back already committed history.

## Typed diff strategies

```ts
import type { HistoryStrategy } from '@ilokesto/state/middleware';

type Delta = { delta: number };
const strategy: HistoryStrategy<number, Delta> = {
  diff: (previous, next) => ({
    forward: { delta: next - previous },
    inverse: { delta: previous - next },
  }),
  apply: (current, patch) => current + patch.delta,
};
const counter = pipe.use(history({
  select: (state: Readonly<{ count: number }>) => state.count,
  restore: (current, count) => ({ ...current, count }),
  strategy,
})).create({ count: 0 });
counter.group(() => {
  counter.set({ count: 2 });
  counter.set({ count: 5 });
});
counter.undo(); // inverse patches in reverse order: 5 -> 2 -> 0
counter.redo(); // 0 -> 5
```

`HistoryDiff<Patch>` contains `forward` and `inverse`. The application must ensure `apply(previous, forward)` yields `next` and `apply(next, inverse)` yields `previous`, under its selection equality. Hooks must be pure and must not mutate state or patches. There is no built-in generic JSON patch assumption: Maps, class instances, or domain operations require suitable typed hooks.

Grouped patches apply backwards in reverse order. After successful replay, the opposite entry is rebuilt from the actual before/after selections, so validation transformations and skipped changes have an accurate reverse transition. A strategy may define rebasing onto later selected changes; the delta example applies relative changes, while default snapshots replace the entire selection.

If `select`, `isEqual`, `filter`, or `diff` throws while recording an already committed transition, history clears its entries and reports the failure through Store notification errors. Replay `apply` runs before dispatch; `restore` runs when middleware forwards the updater, using the current state. If either throws, the replay does not consume its entry and can be retried. Any separate middleware commits remain ordinary undoable changes.

## Reentrancy and persistence

Replay suppression applies only to the replay dispatch, not to user writes from subscribers. Such writes form a new branch and remain undoable. Replay requested while earlier user commits await notification is queued until those commits have been recorded. If middleware commits another user change before the replay itself commits, the restoration becomes a new ordinary transition rather than deleting that intervening history.

Persistence restoration establishes a fresh baseline even when the restored body is equal to the current value. Restored state is not recorded; reentrant user edits after restoration are. `clearHistory()` discards entries and pending commits up to its call boundary; later commits start fresh.

## Timer composition and disposal

History works with `debounce()` and `throttle()` in either declaration order and records actual commits. Pending requests, cancelled updates, dropped calls, and rejected candidates do not create entries.

Undo/redo cancel pending work and cooldowns in **all** timers on this store, even when the requested stack is empty. They do not flush it: replay operates only on committed history. Replay then traverses the normal middleware chain synchronously, bypassing timer delays but still running validation. Rejected replay retains its entry, and validation transformations determine the reverse entry. User writes from replay subscribers are separate dispatches and still obey timing.

Group and pause scopes are evaluated at commit time, not when a timer request is queued. To include delayed work in a synchronous group, flush its timer inside that callback. To commit and save before disposal, flush each timer in pipeline order, then await `store.persist.flush()` if persistence is installed. Persistence flush alone does not run timers.

History owns a commit subscription and its metadata subscriptions. Call `dispose(store)` when it is no longer needed. Disposal clears retained entries, emits a final `disposed: true` snapshot, and releases subscribers. Later ordinary writes still work, but history recording and controls are inactive; a later `group` simply runs its callback. Disposal is idempotent. See [Middleware](/en/state/middleware) for ownership details.

## Control collisions

History adds `undo`, `redo`, `canUndo`, `canRedo`, `clearHistory`, `group`, `pauseHistory`, `resumeHistory`, `getHistoryStatus`, and `subscribeHistory` as immutable enumerable store properties. If the store already has one of these properties, setup throws `HistoryConfigurationError` with code `CONTROL_COLLISION` before installing controls or subscriptions.
