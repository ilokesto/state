# history

`history`는 commit된 state 전이를 기록하고 준비된 store에 undo/redo control을 추가합니다. 전체 snapshot이 기본값이며 selection과 typed patch 전략은 선택 사항입니다.

## Signature

```ts lineNumbers
history(options?: { readonly limit?: number }): PipeAnyMiddleware
history<State, Selection = Readonly<State>, Patch = Selection>(
  options: HistoryOptions<State, Selection, Patch>,
): PipeMiddleware<State>
```

두 overload 모두 결과 store에 `HistoryControls`를 추가합니다. State 전용 overload는 타입을 명시한 hook에서 `State`를 추론하거나 명시적 타입 인자를 받습니다.

| 옵션 | 계약 |
| --- | --- |
| `limit` | Undo entry의 최대 개수이며 기본값은 `300`입니다. 유한한 0 이상의 정수여야 합니다. 그룹은 entry 하나이며 `0`은 entry를 보관하지 않습니다. |
| `filter(previous, next)` | `true`일 때만 commit된 전이를 기록합니다. Middleware 검증 이후의 전체 readonly state snapshot을 받습니다. |
| `select(state)` | 기록할 값을 선택합니다. `restore`와 함께 제공해야 합니다. |
| `restore(current, selection)` | `current`의 추적하지 않는 필드를 보존하면서 전체 state를 재구성합니다. `select`와 함께 제공해야 합니다. |
| `isEqual(previous, next)` | Selection의 동등성 함수이며 기본값은 `Object.is`입니다. 같은 selection은 entry를 만들거나 redo를 무효화하지 않습니다. |
| `strategy` | Typed `diff`/`apply` hook입니다. 생략하면 선택한 snapshot을 보관합니다. |

Control이 있는 store를 받는 API에는 `HistoryStore<State>`를, control만 받는 API에는 `HistoryControls`를 사용하세요. Snapshot은 복제하지 않고 참조로 보관하므로 state, selection, patch를 불변으로 유지해야 합니다.

## 예제

{/* state-example:history-controls */}
```ts
import { history } from '@ilokesto/state/middleware';
import type { HistoryStore } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

const store: HistoryStore<{ count: number }> = pipe
  .use(history({ limit: 20 }))
  .create({ count: 0 });

store.setState({ count: 1 });
store.undo();
store.redo();
store.clearHistory();
```

`undo()`와 `redo()`는 기록한 state를 store에 적용하므로 호환되는 middleware는 replay를 관찰하고 검증할 수 있습니다. 거부된 replay는 재시도할 수 있도록 entry를 유지합니다. Replay가 commit되었다면 이후 본문 subscriber가 예외를 던져도 entry는 이동합니다. `canUndo()`와 `canRedo()`는 가능한 replay가 있는지 보고하고, `clearHistory()`는 current state를 바꾸지 않고 entry를 제거합니다.

Replay에는 `history/undo` 또는 `history/redo` action metadata가 붙어
logger와 DevTools에서 직접 변경과 구분할 수 있습니다.

## 동기 그룹

```ts
const result = store.group(() => {
  store.setState({ count: 1 });
  store.group(() => store.setState({ count: 2 }));
  return 'updated';
});
// result: 'updated'; undo 한 번으로 count가 0으로 돌아갑니다
```

중첩 callback은 바깥 그룹을 공유합니다. 그룹화는 state 알림을 batch 처리하거나 변경을 rollback하지 않습니다. Callback이 예외를 던지면 그룹을 닫고 예외를 전파하되 성공한 commit은 entry 하나로 유지합니다. 빈 그룹, 거부된 쓰기, 동일한 쓰기는 entry를 만들지 않습니다. 시작 selection으로 돌아온 그룹도 entry이며 본문 알림 없이 undo/redo로 소비할 수 있습니다.

첫 번째 변경된 selection은 redo branch를 무효화합니다. 열린 그룹 안의 `undo()`와 `redo()`는 `TypeError`를 던지므로 callback 이후에 호출하세요. Promise를 반환하는 callback은 타입과 런타임에서 거부합니다. 동기 callback만 그룹 범위에 속하므로 async 함수를 전달하거나 그룹이 `await` 이후까지 이어진다고 가정하지 마세요.

## 부분 복원과 필터

```ts
type Editor = { text: string; cursor: number; remote: boolean };

const editor = pipe.use(history({
  select: (state: Readonly<Editor>) => state.text,
  restore: (current, text) => ({ ...current, text }),
  filter: (_previous, next) => !next.remote,
})).create({ text: '', cursor: 0, remote: false });

editor.set({ text: 'hello', cursor: 5, remote: false });
editor.set({ text: 'hello', cursor: 9, remote: false });
editor.undo(); // { text: '', cursor: 9, remote: false }
```

필터는 commit이 아니라 entry를 건너뜁니다. 다음 기록 대상 전이는 앞서 건너뛴 변경을 포함한 실제 current state에서 시작합니다. 필터 자체가 이전 snapshot으로부터 필드를 보호하지는 않습니다. Cursor, 네트워크 상태처럼 undo 대상이 아닌 필드는 `select`/`restore`로 제외하세요. `select`가 매번 새 객체를 반환한다면 동등한 selection을 무시할 수 있도록 적절한 `isEqual`을 제공하세요.

## Pause와 resume

`pauseHistory()`는 새 entry 기록을 중단하고 `resumeHistory()`는 다시 시작합니다. 두 control은 idempotent하며 기존 undo entry를 유지합니다. Pause 중에도 undo/redo를 사용할 수 있습니다. Pause 또는 필터와 관계없이 선택한 값이 바뀌면 오래된 branch를 replay하지 않도록 redo를 무효화합니다. 추적하지 않는 필드만 바뀌면 redo를 유지합니다.

Pause 중에 선택한 필드를 바꾸더라도 기존 snapshot이나 사용자 정의 patch의 영향을 받습니다. Undo 후에도 필드를 보존하려면 해당 쓰기를 pause하는 대신 selection에서 제외하세요.

## 반응형 메타데이터

```ts
import type { HistoryStatus } from '@ilokesto/state/middleware';

const snapshot: HistoryStatus = store.getHistoryStatus();
let undoEnabled = snapshot.canUndo;
const unsubscribe = store.subscribeHistory((status) => {
  undoEnabled = status.canUndo;
});
store.clearHistory(); // 본문이 같아도 메타데이터 listener에 알립니다
unsubscribe();
```

`HistoryStatus`는 readonly `canUndo`, `canRedo`, `undoDepth`, `redoDepth`, `isPaused`, `isGrouping`, `disposed`를 제공합니다. `getHistoryStatus()`는 다음 메타데이터 이벤트까지 참조가 안정적인 frozen snapshot을 반환합니다. `subscribeHistory`는 즉시 알리지 않으므로 현재 snapshot은 별도로 읽으세요.

기록, replay, clear, pause/resume, 그룹 경계, 복원, dispose는 메타데이터 subscriber에 알립니다. 본문 구독만으로는 이 이벤트를 모두 관찰할 수 없습니다. 전달은 registry Store의 FIFO snapshot 계약을 따르며, 같은 callback의 독립적인 중복 등록, unsubscribe 취소, subscriber 오류 수집을 포함합니다. Subscriber 오류는 이미 commit된 history를 rollback하지 않습니다.

## Typed diff 전략

```ts
import type { HistoryStrategy } from '@ilokesto/state/middleware';

type Delta = { delta: number };
const strategy: HistoryStrategy<number, Delta> = {
  diff: (previous, next) => ({
    forward: { delta: next - previous },
    inverse: { delta: previous - next },
  }),
  apply: (current, patch) => current + patch.delta,
};
const counter = pipe.use(history({
  select: (state: Readonly<{ count: number }>) => state.count,
  restore: (current, count) => ({ ...current, count }),
  strategy,
})).create({ count: 0 });
counter.group(() => {
  counter.set({ count: 2 });
  counter.set({ count: 5 });
});
counter.undo(); // inverse patch를 역순 적용: 5 -> 2 -> 0
counter.redo(); // 0 -> 5
```

`HistoryDiff<Patch>`에는 `forward`와 `inverse`가 있습니다. 애플리케이션은 selection 동등성 기준으로 `apply(previous, forward)`가 `next`를, `apply(next, inverse)`가 `previous`를 반환하도록 보장해야 합니다. Hook은 순수해야 하며 state나 patch를 변경하면 안 됩니다. 범용 JSON patch를 가정하지 않으므로 Map, class instance, 도메인 연산에는 적절한 typed hook을 제공해야 합니다.

그룹의 inverse patch는 역순으로 적용합니다. Replay가 성공하면 실제 전후 selection으로 반대쪽 entry를 다시 만들어 검증 변환이나 건너뛴 변경에도 정확한 역전이를 보관합니다. 전략은 이후 selection 변경에 대한 rebasing을 정의할 수 있습니다. Delta 예제는 상대 변경을 적용하지만 기본 snapshot은 selection 전체를 교체합니다.

이미 commit된 전이를 기록할 때 `select`, `isEqual`, `filter`, `diff`가 예외를 던지면 history는 entry를 비우고 Store 알림 오류로 실패를 보고합니다. Replay의 `apply`는 dispatch 전에 실행하고, `restore`는 middleware가 updater를 전달할 때 현재 state를 사용해 실행합니다. 어느 훅이든 예외를 던지면 replay entry를 소비하지 않으며 다시 시도할 수 있습니다. 별도로 발생한 middleware commit은 일반적인 undo 가능한 변경으로 남습니다.

## 재진입과 persistence

Replay 기록 억제는 replay dispatch에만 적용하고 subscriber의 사용자 쓰기는 억제하지 않습니다. 이러한 쓰기는 새로운 branch가 되어 undo할 수 있습니다. 앞선 사용자 commit의 알림이 대기 중일 때 요청한 replay는 해당 commit이 기록될 때까지 대기합니다. Replay 자체가 commit되기 전에 middleware가 다른 사용자 변경을 commit하면 복원을 새로운 일반 전이로 기록하여 중간 history를 지우지 않습니다.

Persistence 복원은 본문이 current value와 같아도 새 baseline을 설정합니다. 복원 state는 기록하지 않지만 복원 이후의 재진입 사용자 수정은 기록합니다. `clearHistory()`는 호출 경계까지의 entry와 대기 중인 commit을 버리며 이후 commit은 새로 기록합니다.

## Timer 조합과 dispose

History는 `debounce()`와 `throttle()`을 어느 선언 순서에서도 지원하며 실제 commit을 기록합니다. 대기 요청, 취소한 update, 드롭된 호출, 검증에서 거부한 candidate는 entry를 만들지 않습니다.

Undo/redo는 요청한 stack이 비어 있어도 해당 store의 **모든** timer에서 대기 작업과 cooldown을 취소합니다. Flush하지 않고 이미 commit된 history만 replay합니다. 이후 일반 middleware chain을 동기로 통과하며 timer 지연만 우회하고 validation은 실행합니다. 거부된 replay는 entry를 유지하고 validation 변환 결과로 반대 entry를 만듭니다. Replay subscriber의 사용자 쓰기는 별도 dispatch이므로 계속 timer를 따릅니다.

Group과 pause 범위는 timer 예약 시점이 아닌 commit 시점에 적용합니다. 지연 작업을 동기 그룹에 포함하려면 callback 안에서 timer를 flush하세요. Dispose 전에 commit과 저장을 마치려면 pipeline 순서대로 timer를 flush한 뒤 persistence가 있다면 `store.persist.flush()`를 기다리세요. Persistence flush만으로 timer가 실행되지는 않습니다.

History는 commit subscription과 메타데이터 subscription을 소유합니다. 더 이상 필요 없을 때 `dispose(store)`를 호출하세요. Dispose는 보관한 entry를 지우고 마지막 `disposed: true` snapshot을 알린 뒤 subscriber를 해제합니다. 이후 일반 쓰기는 가능하지만 history 기록과 control은 비활성화되며 `group`은 callback만 실행합니다. Dispose는 idempotent합니다. 소유권은 [Middleware](/ko/state/middleware)를 참고하세요.

## Control 충돌

History는 `undo`, `redo`, `canUndo`, `canRedo`, `clearHistory`, `group`, `pauseHistory`, `resumeHistory`, `getHistoryStatus`, `subscribeHistory`를 변경할 수 없는 enumerable store property로 추가합니다. Store에 이 property 중 하나가 이미 있으면 control이나 subscription을 설치하기 전에 `CONTROL_COLLISION` code의 `HistoryConfigurationError`를 던집니다.
