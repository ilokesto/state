# 영속 outbox

`createOutbox`는 명시적으로 선택하는 프레임워크 독립 root export입니다. registry
Store, 기존 persistence 제어, `createResource`의 취소 기능을 재사용합니다.
백엔드를 설치하거나 action을 자동 탐색하거나 임의의 상태를 동기화하지 않습니다.

전송 보장은 **at least once**이며 exactly once가 아닙니다. 서버는 인증된 계정 안에서
operation ID를 영속적으로 중복 제거하고, 하나의 ID를 변경되지 않는 작업 하나에
연결하며, 중복 전송에 원래 ACK를 반환해야 합니다. 작업 적용과 idempotency 기록은
서버에서 원자적으로 커밋해야 합니다. 중복 제거 기록은 클라이언트 큐가 재전송될 수
있는 전체 기간 이상 유지해야 합니다.

## HTTP transport와 영속 저장소

다음 브라우저 예제는 한 계정의 인증 정보와 저장 키를 고정합니다. 서버는 커밋 후
`{ status: 'ack', id }`를 반환하거나 HTTP 409와
`{ id, conflict: { amount } }`를 반환합니다. 실제 백엔드 응답은 transport 안에서
검증하세요. outbox도 반환된 ID와 전송한 ID가 일치하는지 확인합니다.

```ts
import { createOutbox } from '@ilokesto/state';
import type { OutboxResponse } from '@ilokesto/state';
import { indexedDBStorage } from '@ilokesto/state/middleware';

type Operation = { readonly amount: number };

function decode(value: unknown): Operation | null {
  if (
    typeof value !== 'object' || value === null ||
    !('amount' in value) || typeof value.amount !== 'number' ||
    !Number.isFinite(value.amount)
  ) return null;
  return { amount: value.amount };
}

export async function openAccountOutbox(accountId: string, token: string) {
  const outbox = createOutbox<Operation, Operation>({
    key: `account:${accountId}:operations`,
    storage: indexedDBStorage({ database: 'application-outbox' }),
    decode,
    online: navigator.onLine,
    async transport(record, { signal }): Promise<OutboxResponse<Operation>> {
      const response = await fetch(`/api/accounts/${encodeURIComponent(accountId)}/operations`, {
        method: 'POST',
        signal,
        headers: {
          'Authorization': `Bearer ${token}`,
          'Content-Type': 'application/json',
          'Idempotency-Key': record.id,
        },
        body: JSON.stringify(record.operation),
      });
      const body: unknown = await response.json();
      if (
        typeof body !== 'object' || body === null ||
        !('id' in body) || typeof body.id !== 'string'
      ) throw new Error('Invalid response ID');
      if (response.status === 409 && 'conflict' in body) {
        const conflict = decode(body.conflict);
        if (conflict) return { status: 'conflict', id: body.id, conflict };
      }
      if (response.ok && 'status' in body && body.status === 'ack') {
        return { status: 'ack', id: body.id };
      }
      throw new Error(`HTTP ${response.status}`);
    },
    resolve: () => ({ action: 'keep' }),
  });

  try {
    await outbox.rehydrate();
  } catch (error) {
    outbox.dispose();
    throw error;
  }
  return outbox;
}

export async function addOperation(
  outbox: Awaited<ReturnType<typeof openAccountOutbox>>,
  id: string,
  amount: number,
) {
  await outbox.enqueue({ id, operation: { amount } });
  return outbox.flush();
}
```

논리 작업마다 `crypto.randomUUID()`로 ID를 한 번 생성해 `addOperation`에 전달하세요.
enqueue 실패 후 같은 논리 작업을 명시적으로 재시도할 때는 ID를 유지하세요.
전송 결과가 불확실하다는 이유로 새 ID를 생성하면 안 됩니다. 새 논리 작업에는
새 ID가 필요합니다. 현재 큐 또는 해당 인스턴스에서 이미 수락한 ID를 다시 사용하면
거절되며 자동 병합하지 않습니다.

작업은 structured clone이 가능하고 선택한 storage adapter가 지원하는 값이어야
합니다. JSON storage는 JSON 호환 값도 요구합니다. 수락한 작업, transport 입력,
공개 snapshot은 복사하므로 외부 변경이 내부 영속 큐를 바꾸지 못합니다.
`decode(unknown)`는 enqueue와 복원 시 실행되며 `null` 반환 또는 예외로 거절합니다.
재시작 후 decode할 때도 작업의 의미를 유지하세요. idempotency key를 유지한 채
payload의 의미를 바꾸는 것은 마이그레이션 방법이 아닙니다.

## API와 관찰

`createOutbox<Operation, Conflict = unknown>(options)`에는 `key`, `storage`,
`decode`, `transport`가 필요합니다. `online`, `retry`, `resolve`는 선택 사항입니다.
transport와 resolver는 `{ signal, key }`를 받으며 `key`는 인스턴스 동안 고정됩니다.

| 제어 | 계약 |
| --- | --- |
| `rehydrate(): Promise<void>` | 명시적으로 저장소를 열고 모든 기록을 검증합니다. 동시 호출은 하나의 시도를 공유하고 실패 후 다시 시도할 수 있습니다. 전송하지 않습니다. |
| `enqueue({ id, operation }): Promise<void>` | hydration 성공 후 사용합니다. 검증한 기록이 저장소에 커밋된 뒤 resolve됩니다. 전송하지 않습니다. |
| `flush(): Promise<ResourceResult<void>>` | 앞선 enqueue가 끝난 후 유한한 큐 snapshot을 전송합니다. 동시 호출은 같은 실행을 공유합니다. |
| `cancel(reason?): void` | 전송과 backoff를 중단하고 ACK되지 않은 작업을 유지합니다. 나중의 flush가 재전송할 수 있습니다. |
| `setOnline(boolean): void` | offline은 전송을 취소합니다. online은 이후 명시적 flush를 허용할 뿐입니다. |
| `dispose(): void` | 영구 취소와 저장소 자원 해제입니다. 영속 큐는 삭제하지 않습니다. |

`flush`는 `data: undefined`를 포함한 `success`, 원래 오류를 포함한 `error`, 또는
사유를 포함한 `cancelled`로 resolve됩니다. rejected promise 대신 이 결과를
처리하세요. `enqueue`와 `rehydrate`는 실패 시 reject됩니다. hydration 전 flush는
`NOT_READY` 오류, offline 또는 dispose 후 flush는 `cancelled` 결과입니다.

각 flush는 캡처한 작업만 순서대로 처리하며 첫 실패에서 멈춥니다. transport 실행
중 추가한 작업도 영속 저장되며 ACK는 최신 큐에서 자신의 기록만 제거합니다.
충돌 replacement를 포함한 새 작업은 다음 명시적 flush를 기다립니다.
따라서 success가 큐 전체가 비었다는 뜻은 아닙니다.

`outbox.store`는 쓰기 메서드가 없는 `ReadableStore<OutboxState<Operation>>`입니다.
snapshot에는 `hydration` (`idle`, `hydrating`, `ready`, `error`), `online`,
`disposed`, `error`, `entries`가 있습니다. 각 entry에는 `id`, `operation`,
`status` (`pending`, `inflight`, `error`), `attempts`, `error`가 있습니다.
시도 횟수와 전송 오류는 메모리 관찰 값이므로 재시작 시 초기화됩니다. backoff 중에는
다음 시도까지 error entry로 보입니다. enqueue 실패는 수락된 entry가 아니라
최상위 error에 표시됩니다.

```ts
import type { Outbox } from '@ilokesto/state';

export function observeQueue(outbox: Outbox<{ readonly amount: number }>) {
  return outbox.store.subscribeSelector(
    state => state.entries.length,
    count => { document.body.dataset.pendingOperations = String(count); },
  );
}
```

scope 종료 시 구독을 해제하고 callback에서 예외를 던지지 마세요. 알림 오류는 이미
커밋한 저장소나 상태를 되돌리지 않습니다. 동기 제어의 알림 오류는 호출자에게 전파됩니다.

## 저장 순서와 복구

outbox는 **명시적으로 선택한 별도 키**와 기존 persistence envelope
`{ state: [{ id, operation }], version: 0 }`를 사용합니다. 기존 키, envelope,
소비자 저장 형식을 마이그레이션하지 않습니다. 잘못된 기록이나 중복 ID는 전체
복원을 거절하며 저장소를 덮어쓰지 않습니다.

순서는 다음과 같습니다.

1. pending 작업을 검증하고 저장소 커밋까지 기다립니다.
2. 그 작업의 ID와 payload를 전송합니다.
3. 해당 ID의 ACK를 받습니다.
4. 그 작업을 제외한 큐를 저장한 뒤에만 제거된 상태를 알립니다.

서버 성공 후 ACK 제거의 영속 저장 전 crash나 저장 실패가 나면 원래 작업이
재전송 대상으로 남습니다. 현재 인스턴스에서 ACK 저장 실패는 error entry이고,
재시작하면 pending으로 복원됩니다. 둘 다 같은 ID를 전송하며 서버의 idempotency
계약으로 중복 효과를 막습니다. 저장 실패는 자동 재시도하지 않습니다.
enqueue를 명시적으로 다시 시도하거나 ACK 저장 실패 후 `flush()`를 다시 호출하세요.

storage adapter는 커밋 후에만 쓰기를 resolve하고 실패를 보고해야 합니다.
at-least-once 전송은 영속 저장소가 유지되고 애플리케이션이 결국 성공적으로 복원과
flush를 수행함을 전제로 합니다. 취소, 영구 장애, 명시적 discard, 저장소 삭제는
전송을 막을 수 있습니다.

## 유한 retry와 online trigger

`retry`가 없으면 **flush당 각 작업에 transport 시도 한 번**만 수행합니다.
명시적 재시도 설정 예는
`retry: { maxAttempts: 3, delayMs: attempt => attempt * 500 }`입니다.
`maxAttempts`는 첫 시도를 포함하는 양의 safe integer입니다. 지연은
0부터 2147483647까지의 유한한 밀리초 값 또는
`(failedAttempt, error) => delay` 함수입니다. 실패한 시도 번호는 1부터 시작하고,
기본 지연은 0입니다. 새 명시적 flush마다 시도 한도가 초기화됩니다.

transport의 throw/rejection만 재시도합니다. 잘못된 ACK, 충돌, resolver 실패,
저장소 실패는 flush를 중단합니다. 무한 재시도, 연결 감지, 주기적 background flush,
브라우저 listener를 자동 설치하지 않습니다.

```ts
import type { Outbox } from '@ilokesto/state';

export function connectNetwork(outbox: Outbox<{ readonly amount: number }>) {
  const online = () => {
    outbox.setOnline(true);
    // Delivery failures remain observable in outbox.store.
    void outbox.flush();
  };
  const offline = () => outbox.setOnline(false);
  window.addEventListener('online', online);
  window.addEventListener('offline', offline);
  return () => {
    window.removeEventListener('online', online);
    window.removeEventListener('offline', offline);
    outbox.dispose();
  };
}
```

## 명시적 충돌 해결

transport는 `{ status: 'conflict', id, conflict }`를 반환합니다. 선택적인
`resolve(record, conflict, context)` callback은 값 또는 promise를 반환합니다.

| 결정 | 효과 |
| --- | --- |
| `{ action: 'keep' }` | `CONFLICT` 코드의 `OutboxError`로 멈추고 작업을 유지합니다. resolver가 없을 때의 기본 동작입니다. |
| `{ action: 'discard' }` | 작업을 적용하지 않고 제거를 명시적으로 저장합니다. 애플리케이션이 해당 손실을 의도적으로 받아들일 때만 사용하세요. |
| `{ action: 'replace', record: { id: freshId, operation } }` | 다른 작업을 보존하며 충돌 기록을 저장소에서 원자적으로 교체합니다. 다음 flush에서 replacement를 전송합니다. |

자동 last-write-wins는 없습니다. 수정한 작업에는 새 ID가 필요하며 원래 ID나 이미
수락한 ID를 재사용하면 `DUPLICATE_ID`로 실패합니다. keep 결정은
`OutboxError.cause`로 충돌 정보를 노출합니다. 사용자에게 선택을 받을 때는 resolver가
promise를 반환하고 `context.signal`을 따라 UI를 취소하도록 구현하세요.
취소 뒤 늦게 도착한 결정은 큐를 교체하거나 삭제하지 못합니다.

## 취소와 계정 소유권

`cancel`과 `dispose`는 취소에 협조하지 않는 transport나 resolver를 기다리지 않고
활성 전송을 종료합니다. signal을 abort하고 backoff timer를 제거하며 늦은 응답이
새 작업을 ACK하지 못하게 합니다. 취소 전에 이미 시작한 ACK 저장은 완료될 수
있으며 취소가 이를 되돌리지 않습니다. enqueue는 전송이 아닌 저장 트랜잭션이므로
`cancel`로 취소되지 않습니다.

dispose는 추가 처리를 막고 소유한 storage adapter를 해제합니다. 이미 시작한
adapter 쓰기나 서버 부수 효과는 되돌릴 수 없습니다. 사용자 adapter와 transport는
cleanup/signal 계약을 지켜야 합니다. dispose 후에는 기존 인스턴스를 재사용하지 말고
새 인스턴스로 rehydrate하세요.

하나의 저장 키에는 활성 소유자 하나만 두세요. cross-tab 또는 multi-process lock은
없으며 같은 키의 동시 소유자는 서로의 큐를 덮어쓸 수 있습니다. 공유하는 storage
factory는 독립적으로 소유할 adapter를 생성해야 합니다.

계정 변경 시 network listener를 제거하고 기존 outbox를 dispose한 뒤 다른 키와 새
인증 정보를 고정한 transport로 새 인스턴스를 만드세요. 기존 transport에서 변경 가능한
전역 인증 정보를 읽거나, 키를 재사용하거나, 다른 계정으로 기록을 이동하면 안 됩니다.
이전 계정의 pending 작업은 원래 키에 남아 해당 계정으로 돌아왔을 때 명시적으로 복구합니다.
