# Durable outbox

`createOutbox` is an opt-in, framework-neutral root export. It uses the registry
Store, the existing persistence controls, and `createResource` cancellation.
It does not install a backend, discover actions, or synchronize arbitrary state.

Delivery is **at least once**, not exactly once. The server must durably deduplicate
operation IDs within the authenticated account, bind each ID to one immutable
operation, and return the original ACK for duplicate delivery. The server must
commit the operation and its idempotency record atomically. Keep that record for
at least the entire replay lifetime of the client queue.

## HTTP transport and durable storage

This browser example captures one account's credentials and storage key. Its
server protocol returns `{ status: 'ack', id }` after commit, or HTTP 409 with
`{ id, conflict: { amount } }`. Validate your actual backend response inside the
transport; the outbox additionally checks that the returned ID matches the sent ID.

```ts
import { createOutbox } from '@ilokesto/state';
import type { OutboxResponse } from '@ilokesto/state';
import { indexedDBStorage } from '@ilokesto/state/middleware';

type Operation = { readonly amount: number };

function decode(value: unknown): Operation | null {
  if (
    typeof value !== 'object' || value === null ||
    !('amount' in value) || typeof value.amount !== 'number' ||
    !Number.isFinite(value.amount)
  ) return null;
  return { amount: value.amount };
}

export async function openAccountOutbox(accountId: string, token: string) {
  const outbox = createOutbox<Operation, Operation>({
    key: `account:${accountId}:operations`,
    storage: indexedDBStorage({ database: 'application-outbox' }),
    decode,
    online: navigator.onLine,
    async transport(record, { signal }): Promise<OutboxResponse<Operation>> {
      const response = await fetch(`/api/accounts/${encodeURIComponent(accountId)}/operations`, {
        method: 'POST',
        signal,
        headers: {
          'Authorization': `Bearer ${token}`,
          'Content-Type': 'application/json',
          'Idempotency-Key': record.id,
        },
        body: JSON.stringify(record.operation),
      });
      const body: unknown = await response.json();
      if (
        typeof body !== 'object' || body === null ||
        !('id' in body) || typeof body.id !== 'string'
      ) throw new Error('Invalid response ID');
      if (response.status === 409 && 'conflict' in body) {
        const conflict = decode(body.conflict);
        if (conflict) return { status: 'conflict', id: body.id, conflict };
      }
      if (response.ok && 'status' in body && body.status === 'ack') {
        return { status: 'ack', id: body.id };
      }
      throw new Error(`HTTP ${response.status}`);
    },
    resolve: () => ({ action: 'keep' }),
  });

  try {
    await outbox.rehydrate();
  } catch (error) {
    outbox.dispose();
    throw error;
  }
  return outbox;
}

export async function addOperation(
  outbox: Awaited<ReturnType<typeof openAccountOutbox>>,
  id: string,
  amount: number,
) {
  await outbox.enqueue({ id, operation: { amount } });
  return outbox.flush();
}
```

Create an ID with `crypto.randomUUID()` once per logical operation and pass it to
`addOperation`. Keep the ID if an enqueue fails and you explicitly retry that same logical
operation; do not generate a new ID for an uncertain delivery. A new logical
operation needs a fresh ID. Duplicate IDs within the queue or an instance's
previously accepted IDs are rejected, never silently merged.

Operations must be structured-cloneable and supported by the storage adapter.
JSON storage additionally requires JSON-compatible values. The outbox copies
accepted operations, transport inputs, and public snapshots so external mutations
cannot change its private durable queue. `decode(unknown)` runs on enqueue and
restoration; return `null` or throw to reject. Preserve the operation's semantic
identity when decoding after restart. Changing a payload's meaning while retaining
its idempotency key is not a migration strategy.

## API and observation

`createOutbox<Operation, Conflict = unknown>(options)` requires `key`, `storage`,
`decode`, and `transport`. Optional fields are `online`, `retry`, and `resolve`.
Transport and resolver receive `{ signal, key }`; `key` is fixed for the instance.

| Control | Contract |
| --- | --- |
| `rehydrate(): Promise<void>` | Explicitly open storage and validate every stored record. Concurrent calls share an attempt; failed attempts can be retried. Does not send. |
| `enqueue({ id, operation }): Promise<void>` | Requires successful hydration. Resolves after storage commits the validated record. Does not send. |
| `flush(): Promise<ResourceResult<void>>` | Deliver a finite queue snapshot after earlier enqueues settle. Concurrent calls share a run. |
| `cancel(reason?): void` | Abort delivery and backoff; retain unacknowledged work. A later flush may replay it. |
| `setOnline(boolean): void` | Offline cancels active delivery. Online only enables an explicit subsequent flush. |
| `dispose(): void` | Terminal cancellation and storage cleanup; does not delete the durable queue. |

`flush` resolves `success` with `data: undefined`, `error` with the original error,
or `cancelled` with a reason. Handle these outcomes rather than relying on a
rejected promise. `enqueue` and `rehydrate` reject on failure. A flush before
hydration returns `NOT_READY`; offline or disposed flushes resolve `cancelled`.

Each flush processes only its captured work, in order, stopping at the first
failure. Enqueues during transport remain durable and an ACK only removes its own
record from the newest queue. New work, including conflict replacements, waits
for the next explicit flush. Success therefore does not mean the queue is empty.

`outbox.store` is a `ReadableStore<OutboxState<Operation>>` with no write methods.
Its snapshot contains `hydration` (`idle`, `hydrating`, `ready`, `error`), `online`,
`disposed`, `error`, and `entries`. Each entry has `id`, `operation`, `status`
(`pending`, `inflight`, `error`), `attempts`, and `error`. Attempts and delivery
errors are in-memory observations, reset after restart. Backoff is observable as
an error entry until the next attempt. Failed enqueues appear in the top-level
error, not as accepted queue entries.

```ts
import type { Outbox } from '@ilokesto/state';

export function observeQueue(outbox: Outbox<{ readonly amount: number }>) {
  return outbox.store.subscribeSelector(
    state => state.entries.length,
    count => { document.body.dataset.pendingOperations = String(count); },
  );
}
```

Unsubscribe your observers at scope end and keep callbacks nonthrowing. Notification
errors do not roll back already committed storage or state. Synchronous control
notification errors propagate to their caller.

## Durability and recovery

The outbox uses a **new, explicitly chosen key** with the existing persistence
envelope `{ state: [{ id, operation }], version: 0 }`. No existing key, envelope,
or consumer storage format is migrated. Invalid records or duplicate IDs reject
the entire restoration without overwriting storage.

The ordering is:

1. Validate and save the pending operation; wait for storage commit.
2. Send that exact operation ID and payload.
3. Receive an ACK for that ID.
4. Save the queue without that operation; only then publish it as removed.

A crash or storage failure after server success but before durable ACK removal
leaves the original operation available for replay. The current instance retains
it as an error entry when ACK saving fails. A restarted instance restores it as
pending. Both resend the same ID; the server's idempotency contract prevents
duplicate effects. Storage failures are not automatically retried. Retry an
enqueue explicitly, or call `flush()` again after an ACK-save failure.

Storage adapters must resolve writes only after commit and report failures.
At-least-once delivery assumes durable storage survives and the application
eventually restores and flushes successfully. Cancellation, permanent outages,
explicit discard, or deleting the storage can prevent delivery.

## Bounded retry and online triggers

Without `retry`, each operation gets **one transport attempt per flush**.
For opt-in retries use, for example,
`retry: { maxAttempts: 3, delayMs: attempt => attempt * 500 }`.
`maxAttempts` includes the first attempt and must be a positive safe integer.
Delay is a finite number from 0 through 2147483647 milliseconds, or a function
`(failedAttempt, error) => delay` with a one-based attempt number. Default delay
is zero. The budget resets on a new explicit flush.

Only transport throws/rejections are retried. Invalid ACKs, conflicts, resolver
failures, and storage failures stop the flush. No infinite retry loop, connectivity
detector, timer-based background flush, or browser listener is installed.

```ts
import type { Outbox } from '@ilokesto/state';

export function connectNetwork(outbox: Outbox<{ readonly amount: number }>) {
  const online = () => {
    outbox.setOnline(true);
    // Delivery failures remain observable in outbox.store.
    void outbox.flush();
  };
  const offline = () => outbox.setOnline(false);
  window.addEventListener('online', online);
  window.addEventListener('offline', offline);
  return () => {
    window.removeEventListener('online', online);
    window.removeEventListener('offline', offline);
    outbox.dispose();
  };
}
```

## Explicit conflict resolution

The transport returns `{ status: 'conflict', id, conflict }`. The optional
`resolve(record, conflict, context)` callback may return a value or promise:

| Resolution | Effect |
| --- | --- |
| `{ action: 'keep' }` | Stop with `OutboxError` code `CONFLICT`; preserve the operation. This is the default without a resolver. |
| `{ action: 'discard' }` | Explicitly save removal without applying the operation; use only when the application intentionally accepts that loss. |
| `{ action: 'replace', record: { id: freshId, operation } }` | Atomically replace the conflicted record in storage, preserving other queued operations. Send the replacement on the next flush. |

There is no automatic last-write-wins. A revised operation must have a fresh ID;
reusing the old ID or another accepted ID fails with `DUPLICATE_ID`. A keep
decision exposes the conflict through `OutboxError.cause`. To ask the user, return
a promise from the resolver and honor `context.signal` when cancelling the UI.
A late resolution after cancellation cannot replace or discard queued work.

## Cancellation and account ownership

`cancel` and `dispose` settle active delivery without waiting for an uncooperative
transport or resolver. Their signals abort, backoff timers are removed, and late
responses cannot acknowledge newer work. A durable ACK write already started
before cancellation may finish; cancellation does not roll it back. Enqueues are
storage transactions, not delivery, so `cancel` does not cancel them.

Dispose blocks further processing and releases the owned storage adapter. An
already-started adapter write or server side effect cannot be undone; custom
adapters and transports must honor their cleanup/signal contracts. After disposal,
create a new instance and rehydrate rather than reusing the old one.

Use one active owner per storage key. There is no cross-tab or multi-process lock;
concurrent owners of the same key can overwrite each other's queues. A shared
storage factory must create independently owned adapters.

On account switch, remove network listeners, dispose the old outbox, and create
a new instance with a distinct key and transport capturing the new credentials.
Do not read mutable global credentials from an old transport, reuse its key, or
move its records into another account. The previous account's pending work stays
under its original key for explicit recovery when that account returns.
